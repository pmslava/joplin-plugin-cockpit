Written 2026-11-11 from three Joplin to-dos of Slava's (ids 0221d9cd273844eea55817821cf93110, 8cbd14f7c12e404a9225ceb5dd5dc9ef, ccdb600ca188444699efc219e948dd00) and their screenshots. The decisions are final for the implementers; a question an agent raises is answered by the manager from this file.

## 0. Rules that apply everywhere

- Every `joplin.*` chain is ONE read-and-call expression (the harness audits the whole tree; see the README banner of src/index.ts for why).
- A write Cockpit makes itself is bracketed (`startOwnWrite` / `afterOwnWrite`, or `applyLocalCreate` for a POST); a call into Jot or Note Tabs is never an own write and gets no bracket.
- Mobile rows never carry `draggable` (Android starts a native drag from a long press); mobile has no multi-select; plugin dialogs draw behind the panel on Android, so mobile asks with in-panel overlays and a `panelToast`, never `showMessageBox`.
- Behaviour lives in pure UMD modules the harness `require()`s (noteMenu.js, rowSelection.js, horizons.js, between.js …); a markup pin in test/run.js is not a substitute for a behavioural check.
- Byte-identical markup where nothing changed: several existing harness checks and e2e specs pin today's markup; a new feature must leave the old markup untouched while it is off.
- Settings that are per device (not synced through the settings note) are registered like `createButtonClick`: `public: true`, `section: 'section'`, a getter in settings.ts.
- Style: 4-space indent; `var` in panelWebview.js and the UMD modules, `var`/`const` as the surrounding code does in TS; double quotes in TS, single in the webview JS; every function has the repo's banner comment (`/** name ****…***/`) saying WHY, in prose; no file-wide reformatting, no renames of existing identifiers, no `#word` in a commit subject.
- Harness: `npm run dist && node test/run.js` (743 checks on main at c723774). New checks go into test/run.js as `await test('…', …)` blocks next to the feature they cover (see each section for where). E2E: ONE new spec per feature, run alone (`E2E_LOCK_WAIT_MS=1800000 xvfb-run -a --server-args="-screen 0 1920x1080x24" npx playwright test e2e/<spec>.spec.ts`) only after `free -g` shows at least 3 GB available and `pgrep -fa e2e-cache | grep -v pgrep` is empty; never the whole suite, never Firefox (there is none here).

## 1. Notes on dates (profile fields)

Owner: "Add in Notes settings: Show notes on the date of creation; Show notes on the date of update. Checkmarks, OFF by default. Both OFF: all notes work as now, shown above or below todos. Any ON: notes shown at the correct date before or after todos (see the setting). Both ON: the same note is shown both on its creation date and on its update date."

Decisions:
- Two profile fields, `notesOnCreated` and `notesOnUpdated`, booleans, default false; a stored profile without them reads false (wherever profiles are normalised today). They mean nothing while `showNotes` is off.
- Both editors (desktop: editorTemplate.ts + editorWebview.js; mobile: the overlay editor in panelWebview.js, `EDITOR_CHECK_IDS` and the read/write around line 4820) show them in the Notes fieldset under "Show regular notes matching the search criteria" and above the "Show notes [Before/After todos]" select. Labels: "Show each note on the day it was created" and "Show each note on the day it was last updated". Plain checkboxes, no enabling logic.
- A note's slot days: its `user_created_time` day when `notesOnCreated`, its `user_updated_time` day when `notesOnUpdated`; both on and the two days equal → once; different → the note is drawn twice, once per day. The timestamp itself is the note's pseudo-due: every rule below is "what the format would do with a to-do due at that instant".
- Per format, with any switch on:
  - Interval: `horizonOf(ts, plan)` names the group. The past is the "Overdue" group (its name does not change for notes); the label rule is the to-dos' (time under a day group, weekday under a week group, date under a month or year group).
  - Date: a heading per day, the union of to-do days and note days, sorted as the format sorts its days; a day with notes only still gets its heading, with that day's `data-drop`.
  - Week planner: the day's section; a note is drawn as a card (the note row markup with the week card's two-zone layout and the time in the head line).
  - Month: the day's dot strip gets a `-note` dot per note slot (same `maxDotsPerDay` cap, counted with the to-dos); the day cell's state class (`-done` / `-overdue` …) is still judged from to-dos alone; the selected day's list under the grid shows the day's notes too.
  - Basic: unchanged (one Notes section, as today).
- Inside a group `notesPosition` decides: `before` → the group's note rows precede its to-do rows; `after` → they follow them (the group's "more" footer stays last). Notes in a group sort by slot time ascending; the to-dos keep their own order.
- The candidate set is exactly the notes the Notes section fetches today (profile criteria, notebook filter, quick filters, the newest-updated `notesLimit` with "show more"): extract the fetch out of `renderNotesSection` so both paths share it; panel.ts fetches once per render and hands the formatter the list through the view state. The "Showing the N most recently updated notes … show more" footer is drawn once at the end of the list when `more` holds. Follow-up, not in 2.11: a range read through the note store for the week and month views.
- With both switches off the old path runs and the old markup is byte-identical. The overview markdown never draws notes (unchanged). The empty-view peek ("Results outside current filters") must count slotted notes as content.
- Row markup: `renderNoteRowHtml` as today (selection, menu, click to open, no drag). A note id may now appear twice in the DOM: selection and picked painting iterate all rows already; check the flash/reveal/scroll-to code tolerates a duplicate.
- Harness (append after the Horizons block in test/run.js): slotting by created / updated / both (same day once, different days twice), position before/after inside a group, Basic unchanged, both-off markup identical, month note dots, editor fields round-trip in both editors. E2E `e2e/notes-on-dates.spec.ts`: a note created in the spec appears under Today with the switch on (Interval), in today's week section (week), and in the selected day's list (month); both switches off → the Notes section as before.

## 2. Pin

Owner: "In Cockpit settings — picker what to do on pin: Own Cockpit pin, Note Tab plugin pin, or both. On Cockpit: Pinned notes show in the section Pinned above Overdue. On Note Tab: see how it is implemented in Jot. Add option to pin note [to the row menu]. Pinned notes/todos should be visible on all profiles, independently from profile."

Decisions:
- Setting `pinTarget` (per device, public, enum): label "Pinning a note", values `cockpit` = "Cockpit's Pinned section" (default), `noteTabs` = "The Note Tabs plugin", `both` = "Both". Description: "What Pin in the row menu does. Cockpit's Pinned section sits above the list in every profile. The Note Tabs plugin must be installed for its tabs. On mobile the Pinned section is used whatever this says."
- Setting `pinnedNoteIds` (per device, private): a JSON array of note ids in pin order (append on pin). Per device, like Note Tabs' own list; syncing it through the settings note is a possible follow-up, not 2.11.
- Row menu: a new item right after Quick edit…, `action: 'pin'`, drawn on desktop and mobile. Labels: single row "Pin" / "Unpin" by that row's state; several rows "Pin N notes" when any is unpinned, "Unpin N notes" when all are. With `pinTarget` = `noteTabs` the labels read "Pin in Note Tabs" / "Pin N notes in Note Tabs" and there is never an Unpin (Note Tabs unpins in its own panel). Mobile reads the Cockpit labels whatever the setting. `menuHtml` gains what it needs in `options` (the pin state of the selection, the target); the harness pins every label.
- The webview learns the pinned set from the markup: each row of a pinned note carries `data-pinned="1"` (rows in the Pinned section included); the setting's value rides in the same render (a data attribute on the list or a data island, the implementer's choice).
- Host: messages `pinNotes` / `unpinNotes` with id arrays. Cockpit target: write the setting, re-render. Note Tabs target: `tabsPinNote([ids])` / `tabsUnpinNote([ids])` (an ARRAY; Note Tabs rejects a bare string); absence is only Joplin's wording "Command not found" / "No such command" / "Cannot execute a command without a runtime" → one `panelToast` per session: "Cockpit: the Note Tabs plugin is not installed or is off." Both: Cockpit's pin always applies, Note Tabs' when it can.
- The Pinned section: a new module `src/core/pinned.ts` with `renderPinnedSection(ids, viewState)`. Records come from the note store when it is ready, else `joplin.data.get(['notes', id], { fields: listingFields })`; a missing (404) or trashed (`deleted_time`) note is dropped from the setting silently. Notebook title/path attached as everywhere; checkbox rings through the same attach as other rows. Markup: `<section class="pinned-section" data-group="pinned"><h2>Pinned</h2>…rows…</section>`, rows via `renderTodoRowHtml` (same options as ordinary rows of the platform, so a pinned to-do drags onto a date target and ticks) and `renderNoteRowHtml`; to-do labels as the Interval format labels its Overdue/Future rows (date and time). Hidden when empty.
- Placement: the first thing in the list in every format, above everything the formatter draws (the Overdue heading, a calendar's navigation included), and above a "before" Notes section.
- Independence: not narrowed by the profile, the notebook filter, the search text or the quick filters. Excluded notebooks still hide (a pin in an excluded notebook is kept, not drawn). Completed to-dos stay pinned. The overview markdown never draws it. The Pinned group takes no between-drop (gate it the way the No-Due group is gated, on `data-group="pinned"`), and its rows do not count as view content for the empty-view peek.
- Harness (append after the NoteMenu block in test/run.js): the labels in every state and target, the settings' registration and getters, the section's markup and placement with stubbed notes, the pruning of a deleted id, the Note Tabs call arguments, the one-per-session toast, no section in markdown. E2E `e2e/pin.spec.ts`: pin from the row menu → "Pinned" heading above "Overdue" with the row; switch profile → still there; unpin → gone.

## 3. A selectable day, the New to-do due date, and the heading menu into Jot

Owner: "Right click on day in Week planner view or on Month view should create a new todo in the Jot with this date selected. Should be new setting in Cockpit settings for the New to-do button — auto-set due date as for picked day. The current day should be highlighted as before, but it should be possible to click on other day, so to see it as selected (not like the current day) — this selection means we are working with this day now. For month this day picker already works. This auto-set setting should be OFF by default, because in many cases the user wants a todo without a due date. Should work on all except Basic. If the setting is OFF we do not need the day picker everywhere — with it OFF it should work as before: the day picker only where needed, the Month view."

Decisions:
- Setting `newTodoDueOnSelectedDay` (per device, public, bool, default false): label "New to-do: due on the selected day". Description: "On: a to-do created from the New to-do button or from a heading's menu is due on the day selected in the panel, at the day start time; today when no day is selected. Every view except Basic then lets you select a day by clicking its heading (the Month view's day picker as before). Off: the button creates a to-do without a due date, and only the Month view has a selected day."
- The selected day is `calendarViewState.selectedDate` (it exists; the month uses it). With the setting ON, in the Interval, Date and Week views a click on a group heading that names a day (`data-drop` holds a date, so Overdue, Future and No Due Date are not selectable) or on a week-day section's heading posts `calendarDaySelected` with that day; the same day clicked again deselects, like the month. The selected heading (and the week-day section) carries `-selected`, visually distinct from `-today`. With the setting OFF these headings carry no click handler and no class: today's markup, byte for byte. The month is unchanged in both states. On mobile the tap selects and the long press opens the heading menu (the existing click swallower keeps the tap from following a long press).
- The due: with the setting on, `runCreateButton` for a to-do computes `due` = the selected day, else today, at the day start time (`getDayStartTime`, "HH:MM", local), and passes it down: `createItem` / `createItemInFolder` take an options object (`inNewWindow`, `due`) and the POST carries `todo_due` for a to-do; the mobile path (`applyNotebookPicked('createTodo')`) applies the same rule, since the setting is per device and the host decides; the Jot route adds `due` (ms) to the `jot.open` arguments.
- The heading menu replaces the heading's direct "open the set-date dialog": a right-click (desktop) or long press (mobile) on a group heading, a week-day heading or a month day cell opens the panel's own context menu with up to two items, built by a pure `headingMenuHtml(day, count)` in noteMenu.js:
  - "New to-do due <day>…" when the heading names a day (<day> as `toLocaleDateString(undefined, { weekday: 'short', day: 'numeric', month: 'short' })`); desktop runs the Jot route with `{ mode: 'new', type: 'todo', notebookId?, due }` and, with Jot absent (callJot's "absent"), today's create-and-open with the due; mobile runs the ordinary mobile create (the notebook overlay under All notebooks) with the due. The due is that day at the day start time. This item does not depend on the setting.
  - "Move 1 to-do to a date…" / "Move N to-dos to a date…" when the group has to-dos: today's action (`requestAlarm` with the group's ids, the selection set to them as now).
  - A heading with neither (an empty No Due Date group) opens nothing, as today.
- Jot: `due` is a new create-mode preset (section 5). A Jot older than 0.5.0 ignores it and the form opens without a date; the Cockpit harness pins the argument, and the e2e spec for the Jot route waits for the Jot release (the release bumps `JOT_E2E_VERSION`).
- Harness (append after the Between block in test/run.js): the setting; no click handlers and no `-selected` with it off; `calendarDaySelected` toggling from a heading; the due computed from the selected day and from today, at the day start; `todo_due` in the POST of the button, of the mobile create and of the heading menu's fallback; `due` in the `jot.open` arguments; the heading menu's labels in all three shapes. E2E `e2e/selected-day.spec.ts`: with the setting on, click a week-day heading → `-selected`; New to-do → the created note's `todo_due` is that day at the day start (read through the data API); right-click the heading → the menu, and its New to-do item (Jot absent in this spec) creates with that due; with the setting off the week-day headings carry no `-selected` after a click.

## 4. The first drag

Owner (desktop, the Interval list, a row dragged into the gap between two rows): "Drag of element to put between other elements almost never works from the first attempt. Only on second one."

Decisions:
- Reproduce before fixing. The regression spec drives a REAL pointer drag with Playwright's mouse (`mouse.move` onto the row, `mouse.down`, `mouse.move` in steps to the lower 40 % band of a target row, `mouse.up`), from a fresh launch, as the FIRST drag of the session, and asserts the due landed between the neighbours (data API). If the mouse drag cannot reproduce it, instrument instead (a webview log of pointerdown / dragstart / each dragover's target and `defaultPrevented` / dragleave / drop / dragend, with `panelPointerIsDown`, `foreignSelectionDragActive`, `panelDragActive` and the iframe's `pointerEvents` at each step), make the log readable from the spec, and report the sequence; the manager then asks the owner for a live trace with a build.
- Hypotheses, in the order to test: (1) the foreign-selection passthrough (`onPanelSelectionDragProbe`) punching the hole in the iframe during the panel's OWN first drag — the `panelPointerIsDown` / `pointercancel` / `pointerType` sequencing on the first press of a session; (2) the inert zones: the row's middle 20 % band and any space between rows that `closest('.todo')` cannot resolve — a release there is a no-op by design, and the first attempt may be an aim at the gap; if so the whole inter-row space becomes a between target; (3) a re-render in flight (the editor-note resync on the parent window's focus, a refresh tick) detaching the source row during the first drag; (4) ordering between the first `dragover` and `onTodoDragStart` raising the flag.
- The fix ships with the spec that failed before it. No change to what a drop does; only to whether the first one is delivered.

## 7. The week and month range read (added 2026-11-11, after the first round)

Owner: "Do this task here" - the follow-up section 1 named. With notes on their days the week planner and the month calendar read the Notes section's candidates, the newest-updated `notesLimit` (1,000) notes, so a note created in the visible week or month but not among them is missing, and "created" on an older month shows almost nothing.

Decisions:
- Scope: the `week` and `month` formats only, and only while `notesOnDates(profile)` holds. Interval, Date and Basic keep the capped set exactly as they are.
- The range is the view's drawn days: the seven days of `buildWeek(anchor, weekStartsOn)`, and the month grid's first to last cell from `buildMonthGrid(anchor, weekStartsOn)` (the outside days of the neighbouring months included, as their to-do dots are). A pure helper (`src/core/calendar.ts` or the noteSlots module) answers `{ fromMs, toMs }` from the profile and `calendarViewState.anchor`: local midnight of the first day to the last millisecond of the last day, built from calendar parts (DST-safe, like horizons.js). panel.ts computes it once per render and passes it to the fetch.
- The store path only. `getNotes` (src/core/joplin.ts) takes an option `range: { fromMs, toMs, byCreated, byUpdated }`; when the view is store-served (`storeServes`, the existing decision) the read is `readStoreNotes`' narrowing - the mirror's notes, the excluded set, the notebook id set, `applyNoteNarrowing` - over the records whose `user_created_time` (byCreated) or `user_updated_time` (byUpdated) lies in the range, with no limit and `more` false; the quick filters and the checkbox scan apply after it as today. A search-served view (criteria with search syntax, typed search text, or a store not ready or unavailable) keeps today's capped set, footer and all: no `created:` / `updated:` search fallback in this change (the search route pages at M²/100 and the capped set is usually complete within a narrow criteria).
- The cache key of the store read carries the range (and the store revision as today), so navigating a week or a month reads afresh and a stale key never serves the neighbouring week.
- The "Showing the N most recently updated notes… show more" footer is not drawn for a range read (nothing was left out); it stays for the capped set.
- A note made or edited now reaches the range through the store as every own write does (`applyLocalCreate` / `applyLocalWrite`); no overlay entry, no ladder, as on every store-served view.
- Cost: a scan of the mirror's note records per render (milliseconds at 20,000) and the ring fill for the drawn rows only, as today.
- README: the sentence in "Views" that says the candidates are the newest 1,000 notes is corrected for the week and month; the DEVLOG's "Not in this change" paragraph of the 2.11.0 entry loses the follow-up and gains one sentence on the range read (2.11.0 is unreleased, so this folds into it; no version bump).
- Harness (next to the notes-on-dates block): the range for week and month from an anchor and both week starts (a month grid spanning five and six weeks); a note older than the cap but created in the visible week appears in its day while the capped set would have missed it (a model fixture of more than `notesLimit` newer notes); the range follows the anchor (previous week / previous month); the updated switch reads by update time and the created switch by creation time; the search-served view unchanged and still capped; no footer on the range read; the cache key apart per range. E2E (`e2e/notes-on-dates.spec.ts`, extended): a note posted with `user_created_time` set to a day of the previous week appears in that week after Previous and in that month's grid and selected-day list; it does not appear in the current week.

## 8. Jot pins in Cockpit too (added 2026-11-11, after the 2.11.0 release; Cockpit 2.11.1 and Jot 0.6.0)

Owner: "We forgot to support from the Jot side the pinning. Now Jot allows to pin the new created note or todo, but only in the Note Tabs. It should be possible to select option to pin it in Cockpit or in both."

Decisions:
- Cockpit's pins are its own private per-device setting, so another plugin pins through a command, as Whereabouts filters and reveals through two. **`cockpit.pinNotes`** is the third entry of the cross-plugin contract, registered beside `cockpit.filterByNotebook` and `cockpit.revealNote` on both platforms, label "Cockpit: pin notes", no menu or toolbar item. Argument: an array of note ids (a bare string is taken as one id). It pins them in **Cockpit's Pinned section only** - never Note Tabs, whatever the `pinTarget` setting says, because the caller decides where it pins - through the same path the row menu's Pin uses (append to `pinnedNoteIds`, re-render; an id already pinned is left where it is; no own-write bracket, Cockpit writes no note). Total on its input: an empty or malformed argument warns and returns; a note that does not exist yet is pinned all the same (the Pinned section's own pruning drops an id whose note is gone or trashed on the next render). Resolves `{ pinned: string[] }`, the ids now in the list. Cockpit 2.11.1: the version in its four places and the harness pin; the harness's command-contract checks gain the name and the label; README "Commands for other plugins" (the third command) and a sentence in "Works with Jot"; a DEVLOG entry.
- Jot keeps its `noteTabs` setting key and values (Not used / Pin / Don't pin: whether the form draws the row and where the row starts), relabelled **"Pin the new note"**, and gains **`pinTarget`**, "Where the new note is pinned": `noteTabs` = "Note Tabs" (the default, today's behaviour), `cockpit` = "Cockpit's Pinned section", `both` = "Note Tabs and Cockpit". The form row's label names the target - "Pin in Note Tabs", "Pin in Cockpit", "Pin in both" - with the same Pin / Don't pin buttons; the setting's description says each needs its plugin. On Pin, after the tags and before any open, as today: Note Tabs → `tabsPinNote([id])`; Cockpit → `joplin.commands.execute('cockpit.pinNotes', [id])`; both → both, in that order, each failure its own. Absence is Joplin's command-service wording only ("Command not found", "without a runtime"), said once a run per plugin: Cockpit's message "Jot: the note is created, but Cockpit is not installed or is off, so it was not pinned there." The create result's `pinned` is true when any target pinned. Mobile is the same (Cockpit's section exists there). Jot 0.6.0: the version everywhere its harness pins; README (the setting, the row, a line in the Cockpit paragraph); the DEVLOG entry; `jot.open`'s resolve shape unchanged.
- Jot's e2e installs Cockpit beside it as it installs Note Tabs: `scripts/setup-e2e.sh` fetches `https://github.com/pmslava/joplin-plugin-cockpit/releases/download/v${COCKPIT_E2E_VERSION}/io.github.pmslava.cockpit.jpl` into `.e2e-cache/io.github.pmslava.cockpit-<version>.jpl` (2.11.1, pinned in tests.yml and launch.ts like Note Tabs' 1.4.0), `launchJoplin({ extraPlugins })` carries it, and one spec creates through `jot.open` with the target on Cockpit and finds the note under Cockpit's "Pinned" heading. Locally the Cockpit build from this round stands in for the release until it exists. Cockpit releases first, Jot after; Cockpit's `JOT_E2E_VERSION` moves to 0.6.0 in a later docs-only commit.
